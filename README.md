# `#[cube] fn` takes up its name as a module

Minimal reproduction for cubecl 0.11.0: a `#[cube]` function can't share a name with a
module, even though plain Rust allows a function and a module to have the same name.

```
error[E0428]: the name `scale` is defined multiple times
  --> src/lib.rs:36:5
   |
34 |     pub mod scale {}
   |     ------------- previous definition of the module `scale` here
35 |
36 |     #[cube]
   |     ^^^^^^^ `scale` redefined here
   |
   = note: `scale` must be defined only once in the type namespace of this module
```

## Run it

```sh
cargo build                               # controls and workaround, compiles
cargo build --features definition_clash   # fails: E0428
cargo build --features import_clash       # fails: E0255 + E0425
```

`src/lib.rs` has four modules:

- `plain`: the same two patterns without `#[cube]`. Compiles.
- `definition_clash`: a `#[cube] fn scale` next to `mod scale {}`. Fails with E0428.
- `import_clash`: `mod interpolation` holds `#[cube] fn interpolation`, which a kernel next
  to the module imports with `use interpolation::interpolation;`. Fails with E0255 on the
  `use` and E0425 on the call.
- `workaround`: the same as `import_clash`, but without the `use`. The kernel calls
  `interpolation::interpolation::<F>(...)` by its full path. Compiles.

## What happens

Rust keeps functions in the value namespace and modules in the type namespace, so
`fn scale` and `mod scale` can sit side by side. `#[cube]` also generates a module with the
function's name, to hold `expand` and the launch code
(`cubecl-macros-0.11.0/src/generate/launch.rs:31`, `#vis mod #name { use super::*; ... }`).
The expansion of `definition_clash`, from `cargo rustc --lib --features definition_clash -- -Zunpretty=expanded`:

```rust
pub mod scale {}                                        // the user's module

pub fn scale<F: Float>(x: F) -> F { x * F::new(2.0) }   // the user's function
pub mod scale {                                         // generated by #[cube]: clashes
    use super::*;
    pub fn expand<F: Float>(scope: &cubecl::prelude::Scope, x: ...) -> ... { ... }
    ...
}
```

Calls inside cube code are rewritten to `<path>::expand(scope, ...)`
(`cubecl-macros-0.11.0/src/generate/expression.rs:212` and `:225`), so the generated module
also has to be reachable by the same path as the function:

```rust
interpolation::expand::<F>(scope, ...)                  // import_clash: resolves to the user's
                                                        //   `mod interpolation`, no `expand`
interpolation::interpolation::expand::<F>(scope, ...)   // workaround: resolves correctly
```

In `import_clash` the `use` brings both the function and the generated module into scope.
The module collides with `mod interpolation` (E0255), and the rewritten call then resolves
`interpolation::expand` to the user's module, which has no `expand` (E0425).

The practical result is that a `#[cube]` function's name must not match any module (or
other type-namespace item) that is in scope where the function is defined or imported.
Naming a function after the module it lives in, such as `interpolation::interpolation`,
is a common Rust pattern and is where we hit this.

## Possible fix

Give the generated module a name users won't write, such as `__cube_scale`, and rewrite
call sites to `<path>::__cube_scale::expand`. The user's function name would then occupy
only the value namespace, as it does in plain Rust.

## Workarounds

- Call the function by its full path instead of importing it.
- Give the function a name that doesn't match a module in scope.
- Make it a method in a `#[cube] impl` block. Methods don't generate a module.

## Unrelated note

The kernels in this crate use `::<F>` on their calls. Without it, 0.11.0 fails with
`E0283: type annotations needed` when calling a generic `#[cube]` function with
`input[ABSOLUTE_POS]` from a `&[F]` kernel argument. This happens with or without a name
clash, so it is kept out of the way here.
